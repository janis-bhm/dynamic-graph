# `top_tree` crate guide

`top_tree` is the generic dynamic-forest layer used by `find_bridge`, its only consumer. It maintains a binary top tree over a forest and lets an application attach a summary, a label weight, and an edge weight to every cluster. It implements the forest and cluster machinery; bridge, cover-level, and graph-update policy live in `find_bridge`.

Nightly Rust is required: `src/lib.rs` enables `pattern_types`, `pattern_type_macro`, and `structural_match` (`#![expect(internal_features)]`). The workspace is `edition = "2024"`, `resolver = "3"`, members `crates/*`. The sibling crate `splay_top_tree` (`bitflags` + `bit_field`) is a separate, older implementation; `top_tree` does not depend on it and the two must not be conflated.

## Structure

- `src/lib.rs` (519 lines) declares the modules and re-exports `summary::{Boundary, MergeContext, Summary}`, `top_tree::{ClusterId, ClusterWeight, NodeKind, TopTree}`, and the `tree` handles (`Edge`, `EdgeId`, `Label`, `LabelId`, `Node`, `SwapResult`, `Tree`, `VertexId`). It also holds crate infrastructure: the `impl_nonmax_type!` macro generating the niche-optimized `NonMaxUsize`/`NonMaxIsize`/`NonMaxU32`/`NonMaxI32` newtypes (each `repr(transparent)`, with `Option<T>` the same size as the integer), `Generation(u32)` for invalidating recycled handle slots, a private packed-`u64` `BitVec` for exposure and occupancy flags, and `pub mod slot`: the arena `SlotVec<T, I: Indexing = NonMaxUsize>` (union slots, free list, `push`/`push_with`/`remove`/`replace`/`get`/`get_mut`/`iter`/`for_each_mut`, `Index`/`IndexMut`) plus the `Indexing` and `OptionalIndexing` traits. `SlotVec` replaced the external `slotvec` crate; do not reintroduce that dependency.
- `src/summary.rs` (145 lines) defines the application contract: `Boundary`, `MergeContext`, and `trait Summary`. `tree_edge(e: ClusterId)` and `label(l: ClusterId)` build leaf summaries from the *leaf's* `ClusterId`; `combine(left, right, ctx)` builds a parent value; `flip` handles reversal; `apply`/`compose` handle lazy tags.
- `src/top_tree.rs` (1782 lines) implements `TopTree<S, N = (), E = ()>` and the cluster tree. A cluster is a leaf for a forest edge (carrying `E`) or an attached label (carrying `N`), or an internal union of two clusters sharing a vertex. This file owns cluster boundaries, splay/rotation and expose logic, link/cut/attach/detach, summary recomputation, and lazy-tag propagation.
- `src/tree/mod.rs` (1031 lines) is the generic forest storage `Tree<V, E, L>`, instantiated by `TopTree` as `Tree<(), ClusterId, ClusterId>`. It holds generation-tagged `VertexId`, `EdgeId`, and `LabelId` (each with a `generation()` accessor), `Node<V>`, `Edge<W>`, `Label<W>`, `SwapResult<Id>`, the public `LabelWalker`/`LabelWalkerMut` incidence iterators (plus private edge walkers) and a `VecExt` swap-remove helper. It does not maintain top-tree summaries.
- `src/top_tree/tests.rs` (1300 lines, 20 tests) and `src/tree/tests.rs` (102 lines, 3 tests) hold the crate's tests: cluster invariants, randomized link/cut/expose sequences and custom summaries in the former, forest storage and handle reuse in the latter. The former does not compile; see the WIP section.

## Data model and invariants

- A cluster has zero, one, or two boundary vertices. Two boundaries make it a *path cluster*; zero or one make it a *point cluster*. The parent is the union of its children at their shared central vertex. These shapes determine whether a child contributes its path to the parent's path.
- Tree-edge leaves represent the dynamic forest. Label leaves are attached to one vertex and can represent vertex-local data or non-tree edges. `find_bridge` attaches one label leaf per vertex for its summaries.
- `TopTree<S, N, E>` is generic over the summary `S`, the label-leaf weight `N`, and the tree-edge weight `E` (both defaulting to `()`). `link(u, v, weight: E) -> ClusterId` and `attach(v, weight: N) -> ClusterId` return the new leaf's handle; `cut(u, v) -> Option<E>` returns the removed edge's weight (`None` if there is no such edge); `detach(label: LabelId)` returns nothing. `add_vertex() -> tree::VertexId` and `remove_vertex(vertex) -> Option<SwapResult<tree::VertexId>>` maintain the forest. `expose`, `expose_path`, `expose_path_tagged`, `deexpose`, and `component_summary` return `Option<S>` and require `S: Clone`; `expose_path_node` returns the `ClusterId` of the exposed path root. Node inspection for guided descents: `node_summary`, `node_is_path`, `node_boundary`, `node_children`, `node_central`, `node_kind`, `node_label_key`, `leaf_weight`/`leaf_weight_mut`, `push_node_tag`, `cluster_vertex`, `edge_endpoints`, `label_clusters`, `first_label`, `connected`, `connected_clusters`, `update_label_summary`, `update_label_summary_by_cluster`.
- A `TopTree` holds the forest, a `SlotVec` arena of cluster nodes (live slots are tracked so a freed slot is never read as a cluster), and a `BitVec` of currently exposed vertices. Each cluster node keeps parent/child links, a `flipped` orientation flag, its boundary vertices, the `S` summary, and a pending `S::Tag`.
- `MergeContext` is the authority for boundary-aware combination. Path aggregates should include only path children; a raked point child is off the parent path. Tags propagate only to path children: `push_tag` leaves raked children untouched.
- Reversing a cluster changes the logical left/right order, so a direction-dependent summary must implement `Summary::flip` consistently. `apply` updates a cluster summary in place. `compose(tag: &mut Self::Tag, parent: &Self::Tag)` takes the *child's* pending tag first and the tag being pushed down second; the top tree calls it as `S::compose(&mut child.tag, &parent_tag)`, so the order of pending operations must be preserved.
- Structural changes and exposes can change cluster boundaries and orientation. Recompute summaries through `Summary::combine` rather than assuming a cluster's old shape or child order is stable.
- Identity: `VertexId`/`EdgeId`/`LabelId` are generation-tagged and their slots are recycled, so removal invalidates them, and `remove_vertex` may swap the last element of storage and return a `SwapResult` telling you which handle moved. The top tree fixes up its own boundary bookkeeping on that swap; summaries carry no vertex-remap hook. Applications should hold the `ClusterId` of a label leaf as the stable vertex identity — what `find_bridge` does — and re-derive `tree::VertexId` on demand with `cluster_vertex` instead of storing raw vertex IDs in a summary.

## Working in this crate

For a new application aggregate, implement `Summary` and keep application-specific state in that summary and its tag. Use `MergeContext` to distinguish path and point contributions. The bridge-specific example is `find_bridge::CoverLevel` (used as `TopTree<CoverLevel, VertexLabels, EdgeId>`); keep bridge policy out of the generic forest storage.

The public node-inspection methods exist for algorithms such as `find_bridge`'s `find_first_label` that must descend an exposed cluster. Read children through the logical (flip-aware) accessors and call `push_node_tag` before inspecting child summaries.

## Paper references

The algorithm built on this crate is described in [*Dynamic Bridge-Finding in O(log² n) Amortized Time* by Holm, Rotenberg, and Thorup (2017)](../../papers/Dynamic%20Bridge-Finding%20in%20O%28log2%20n%29%20Amortized%20Time%20%28holm%2Crotenberg%2Cthorup%29.txt). Section 2 specifies the dynamic-tree operations used by the reduction, and Section 3 defines top-tree clusters, boundaries, and expose. The `Summary` interface is the application's way to maintain the Section 4 cover-level information over those clusters; that specialization is in `find_bridge/src/cover_level.rs`.

The bridge paper treats top trees as an abstract data structure. The concrete splay/rotation mechanics are implemented in `src/top_tree.rs`; the companion `../../papers/Splay Top Trees (Holm, Rotenberg, Ryhl).txt` gives background on that implementation style, and [*Maintaining Information in Fully-Dynamic Graph Problems* (Alstrup, Holm, Lichtenberg, Thorup)](../../papers/Maintaining%20Information%20in%20Fully-Dynamic%20%28alstrup%2Cholm%2Clichtenberg%2Cthorup%29.txt) and [*Poly-Logarithmic Deterministic Fully-Dynamic Algorithms for Connectivity, Minimum Spanning Tree, 2-Edge, and Biconnectivity* (Holm, Lichtenberg, Thorup)](../../papers/Poly-Logarithmic%20Deterministic%20Fully-Dynamic%20Algorithms%20for%20Connectivity%2C%20Minimum%20Spanning%20Tree%2C%202-Edge%2C%20and%20Biconnectivity%20%28holm%2Clichtenberg%2Cthorup%29.txt) cover the general top-tree maintenance background.
